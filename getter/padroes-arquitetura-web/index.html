APIs

Padrão de APIs REST

Contrato OpenAPI 3.x

  • Spec-first: o contrato é revisado antes do código
  • Geração de clientes, docs e mocks automáticos
  • FastAPI gera o OpenAPI nativamente; NestJS via @nestjs/swagger

Evolução Versionamento

  • Versionar a URL (/api/v1/...) para contratos públicos
  • Semantic versioning para o contrato interno
  • Depreciação com janela mínima de 2 releases

Robustez Erros padronizados

  • Formato único: RFC 7807 (Problem Details)
  • Status codes corretos (400/401/403/404/409/422/429/5xx)
  • request_id em toda resposta de erro

Escala Paginação & idempotência

  • Paginação por cursor em listas grandes
  • Idempotency-Key em POSTs críticos (pagamentos, webhooks)
  • Filtros, ordenação e campos via query params explícitos
APIs

Contrato de erro padrão

RFC 7807 — todas as APIs da Getter respondem erros neste formato.

{

Alta carga

gRPC para comunicação interna

  • HTTP/2: multiplexação, header compression, menor latência
  • Protobuf: payload binário ~5–10× menor que JSON
  • Streaming unário, server-stream, client-stream e bidirecional
  • Code generation em Python e TypeScript a partir do mesmo .proto
  • Deadlines & cancellation nativos por chamada
⚠️
Usar gRPC só internamente (mTLS na mesh/serviço). Expor REST na borda.
syntax = "proto3";
package getter.product.v1;

service ProductService {
  rpc GetProducts(ProductRequest)
      returns (stream Product);          // server-streaming
}

message ProductRequest {
  repeated string ids = 1;
  bool include_price = 2;
}

message Product {
  string id = 1;
  string name = 2;
  double price = 3;
}
Assíncrono

Mensageria: eventos & filas

Event-driven Publicar / Subscrever

  • Eventos de domínio: order.created, pizza.registered
  • Produtor não conhece consumidores → desacoplamento total
  • Replays e projeções (CQRS) para leitura escalável
  • Ferramentas: Kafka (alto throughput, retenção) · RabbitMQ (roteamento flexível)

Trabalho Filas / Jobs

  • Tarefas de longa duração: e-mail, PDF, ML, integrações externas
  • Retry com backoff exponencial + DLQ (dead-letter queue)
  • Consumidores idempotentes — processar 2× ≠ efeito duplicado
  • Ferramentas: RabbitMQ, BullMQ (Node), Celery/ARQ (Python)
🧭
Decisão rápida: precisa da resposta na mesma request → síncrono (gRPC/REST). Pode ser processado depois / muitos consumidores → assíncrono (mensageria).
Confiabilidade

Padrões de resiliência

⏱ Timeouts

Todo cliente de rede tem timeout explícito. Em gRPC, via deadline. Sem timeout = falha em cascata.

🔁 Retries

Retry apenas em falhas transitórias (5xx/timeout), com backoff exponencial + jitter. Nunca retry em 4xx.

⛔ Circuit breaker

Após N falhas, abre o circuito e falha rápido por um período. Evita sobrecarregar dependência doente.

🪣 Bulkhead

Isola dependências por pool de conexões/threads. Uma dependência lenta não derruba as demais.

🧰
Ferramentas: Python → tenacity, circuitbreaker · Node/TS → opossum, p-limit · malha de serviços → Istio/Linkerd (timeouts, retries, circuit breaking declarativos).

Stack · Python

Padrões FastAPI

  • Estrutura por domínio (não por camada técnica): routes / services / repositories / schemas
  • Pydantic v2 para schemas de entrada/saída — nunca dict cru
  • DI via Depends para DB, auth e serviços — testável
  • Lifespan para startup/shutdown (pools, migrations)
  • Async só até o banco: SQLAlchemy async ou asyncpg
from fastapi import APIRouter, Depends, HTTPException
from pydantic import BaseModel

router = APIRouter(prefix="/api/v1/users")

class UserCreate(BaseModel):
    email: EmailStr
    name: str

@router.post("", status_code=201)
async def create_user(
    payload: UserCreate,
    db: Session = Depends(get_db),
):
    user = await user_service.create(db, payload)
    return UserOut.model_validate(user)
⚠️
Bloquear operações síncronas pesadas no event loop (CPU-bound → run_in_executor ou worker separado).
Stack · TypeScript

Padrões NestJS

  • Módulos por domínio: Module → Controller → Service → Repository
  • DTOs com class-validator + ValidationPipe global (whitelist: true)
  • Guards para authz (RBAC/claims), Interceptors para logging e request_id
  • @nestjs/swagger para gerar OpenAPI a partir de decorators
  • Testes com supertest + módulos de teste isolados
// users.controller.ts
@Controller('api/v1/users')
export class UsersController {
  constructor(private readonly users: UsersService) {}

  @Post()
  @HttpCode(201)
  create(@Body(new ValidationPipe({ whitelist: true }))
         dto: CreateUserDto) {
    return this.users.create(dto);
  }
}
⚠️
Cuidado com CPU-bound no event loop do Node — use workers/filas para processamento pesado.
Stack · Frontend

Padrões Next.js

  • App Router + Server Components por padrão; client components só quando há interatividade
  • Dados via Server Components / Route Handlers — nunca expor secrets no client
  • Cache consciente: ISR para conteúdo, revalidação sob demanda
  • BFF: Route Handlers como proxy autenticado para APIs internas
  • TypeScript strict + Zod para validação de dados externos

GitLab

Repositórios & fluxo de trabalho

Estrutura Repositórios

  • 1 serviço = 1 repo (ou monorepo por domínio, decidido por time)
  • Branch principal: main — sempre deployável
  • Fluxo: trunk-based com branches curtos de feature (2–3 dias)
  • Nomes padronizados: feat/, fix/, chore/

Qualidade Merge Requests

  • MR obrigatório — push direto em main bloqueado
  • Pipelines verdes antes do merge (gate obrigatório)
  • Code review com pelo menos 1 approver
  • Branch protegida: sem force push, sem deleção
  • Convenção: Conventional Commits (feat, fix, refactor, docs, test, chore)

lint:
  stage: lint
  script: [npm run lint, npm run typecheck]

test:
  stage: test
  script: [npm run test -- --coverage]
  coverage: '/All files[^|]*\|[^|]*\s+([\d.]+)/'

scan:
  stage: scan
  script:
    - semgrep ci                    # SAST
    - gitleaks detect               # segredos
    - trivy image $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA  # container

deploy:
  stage: deploy
  environment: production
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

Reforço de segurança no pipeline

SAST Análise estática

Semgrep/Bandit (Python), ESLint security (TS). Falha bloqueia o merge — sem exceção silenciosa.

Secrets Detecção de segredos

Gitleaks + pre-commit hook. Segredo vazado = revogação imediata, não apenas remoção do commit.

Deps Dependency scanning

Trivy / Renovate com update automático e alerta de CVEs críticas (severity high+).

Container Imagens seguras

Base slim e assinada, scan de vulnerabilidades, sem root, read-only filesystem.

Runner Runners confiáveis

Runners privados da empresa; DOCKER_HOST restrito; sem jobs privilegiados.

Supply Integridade

Artefatos assinados, SBOM gerado por imagem e registro privado com acesso mínimo.

Segurança

Segurança em integrações

  • AuthN: OAuth 2.0 + OIDC (single sign-on) — tokens JWT curtos, escopos mínimos
  • AuthZ: claims/roles no token, verificados por guard/middleware
  • Serviço↔serviço: mTLS ou client credentials com escopo restrito
  • Segredos: GitLab CI Variables (protegidas) + Vault/Secret Manager — nunca no código
  • Transporte: HTTPS obrigatório; HSTS; CORS restrito por origem
  • ❌ Segredos em .env versionado ou variáveis NEXT_PUBLIC_* sensíveis
  • ❌ Tokens de longa duração sem rotação
  • ❌ Rate limiting ausente em endpoints públicos
  • ❌ Webhooks sem assinatura/validação de payload
  • ❌ Logs com dados pessoais ou credenciais
🛡️
Padrão: autenticação centralizada (OIDC) · autorização em cada serviço · segredos em cofre · auditoria de acessos.
