The Problem

😰 Without automation

  • Deploys are manual & scary
  • Feedback comes days after the change
  • “It works on my machine”
  • Regressions reach production silently
  • Deploy day = firefighting day

🚀 With CI/CD

  • Every change is verified automatically
  • Feedback in minutes
  • One reproducible path to production
  • Rollbacks are cheap & fast
  • Deploys become boring (good!)

CI/CD = Speed with Guardrails

Continuous Integration: merge often, verify every merge.

Continuous Delivery: every commit is potentially releasable.

Commit→ Test→ Build→ Scan→ Deploy
The core idea Automation gives us speed; the pipeline gives us control. We don’t slow down to be safe — we verify continuously so we never have to stop.

Why It Matters for Us

  • Small changes shipped often = less risk per release
  • Fast feedback loop = better developer experience
  • Automated checks = consistent quality bar, not reviewer roulette
  • Auditable pipeline = confidence to move fast on Getter products

Automated Testing: The Safety Net

CI/CD without tests is just automated deployment of bugs.

Tests are the control in “Accelerate with Control”.

The Test Pyramid

            /\
           /  \        E2E / UI        few, slow, brittle
          /----\        Integration     some, medium
         /------\       Unit            many, fast, cheap
        /--------\
        Unit  Integration  E2E
        (many, fast)   (few, slow)
  • Unit — one function/class, mocked deps → milliseconds
  • Integration — DB, APIs, real modules → seconds
  • E2E — user journeys, real stack → minutes

Test Principles

✅ Fast

Developers run them locally before committing. If tests are slow, nobody runs them.

✅ Reliable

No flaky tests. A flaky suite teaches the team to ignore red builds.

✅ Meaningful

Test behavior, not implementation. High coverage ≠ good tests.

Guard the pipeline Enforce coverage thresholds and block merge on failures — otherwise tests become decoration.

CI/CD as a Testing Accelerator

  • Run the full suite on every MR — not just “the changed parts”
  • Run fast checks first: lint → unit → integration → e2e (fail early)
  • Parallelize jobs & use test splitting to keep the loop short
  • Publish test reports & coverage so MRs show the impact visually
  • Add contract tests between services to catch breaking API changes

CI/CD Pipeline Best Practices

The pipeline is code. Treat it with the same rigor as application code.

Pipeline as Code

Declarative pipelines live in the repo, versioned & reviewed like any other change.

# .gitlab-ci.yml (example)
stages: [lint, test, build, scan, deploy]

lint:
  stage: lint
  script: npm run lint

test:
  stage: test
  script: npm run test:ci
  artifacts:
    reports:
      coverage_report:
        coverage_format: cobertura
        path: coverage/cobertura-coverage.xml

build:
  stage: build
  variables:
    IMG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
  script:
    - docker build -t "$IMG" .
    - docker push "$IMG"
Why? Reviewable, auditable, reproducible. No more “the pipeline on my machine”.

Deterministic Builds

✔ Do

  • Commit lockfiles (package-lock.json, yarn.lock, poetry.lock)
  • Pin base images & tool versions
  • Use immutable artifacts (image digest, not :latest)
  • Cache dependencies, not build output

✘ Avoid

  • npm install without lockfile → surprises
  • :latest tags anywhere
  • Installing tools at runtime inside jobs
  • Non-reproducible “works yesterday” builds

Speed Without Cutting Corners

⏱ Cache smartly

Cache node_modules / ~/.cache keyed by lockfile hash. Cache Docker layers.

🎯 Fail fast

Order stages: cheap & fast checks first. Don’t build before linting.

🔀 Parallelize

Split test suites across runners. Matrix builds for Node versions / browsers.

📦 Artifacts, not rebuilds

Build once, promote the same artifact through environments.

Environment Parity & Rollbacks

  • Dev / staging / prod should run the same artifact — only config differs
  • Deploy with feature flags to release code without exposing it
  • Automate rollback: one click/command back to the previous artifact
  • Keep secrets in a vault / CI variables — never in the repo
  • Use zero-downtime strategies (blue/green or canary) for critical services
Golden rule If deploying is scary, deploy more often — until it isn’t.

Security Scanners in the Pipeline

Shift Left Find vulnerabilities where they’re cheapest: before merge.

A vulnerability found in CI costs minutes. In production, it costs an incident.

Scanner Categories

🔍 SAST — Static Analysis

Scans source code for vulnerabilities & bugs. Semgrep, CodeQL, SonarQube, ESLint security plugins.

📦 Dependency / SCA

Checks libraries & licenses against vulnerability DBs. Trivy, Grype, Dependabot, Renovate, npm audit.

🔑 Secret Scanning

Detects keys, tokens & passwords committed by accident. gitleaks, trufflehog, GitLab secret detection.

🐳 Container Scanning

Scans images & OS packages for known CVEs. Trivy image, Grype, Docker Scout.

Where Each Scanner Runs

Commit→ Secret scan→ SAST→ SCA deps→ Build→ Image scan→ Deploy
  • Secret scan + SAST: on every commit / MR — instant feedback to the author
  • SCA: on every MR + scheduled daily (new CVEs appear all the time)
  • Image scan: after build, before the artifact is promoted
  • DAST: against a deployed staging environment (OWASP ZAP) — fewer, scheduled runs

Example: Security Stage

# .gitlab-ci.yml (example)
scan:
  stage: scan
  parallel:
    matrix:
      - TOOL: [secrets, sast, deps]
  script:
    - case "$TOOL" in
        secrets) gitleaks detect --source . --report-format json ;;
        sast)    semgrep scan --config auto --json ;;
        deps)    trivy fs --scanners vuln,secret --exit-code 1 --severity HIGH,CRITICAL . ;;
      esac
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

image-scan:
  stage: scan
  script:
    - trivy image --exit-code 1 --severity HIGH,CRITICAL $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
  needs: [build]
Policy Block merge on HIGH/CRITICAL findings. Track MEDIUM as debt in the issue tracker. Never ship known-critical vulnerabilities.

Security Culture Tips

  • Fail the pipeline on secrets found — and rotate immediately when one slips through
  • Keep dependency updates frequent; small updates are easier than a Friday “upgrade everything”
  • Generate an SBOM (CycloneDX/SPDX) with each release — you can’t fix what you can’t inventory
  • Don’t ignore scanner noise: tune rules, but never silence everything
  • Treat the pipeline itself as a security boundary — protect CI variables & runners

Commit Best Practices

History is documentation. Write it for your future self and your reviewers.

Atomic Commits

✔ One logical change per commit

  • Easy to review, revert, bisect
  • “Fix bug X” should not also rename 40 files
  • Each commit leaves the codebase working

✘ Anti-patterns

  • “WIP”, “changes”, “fix”, “update” (meaningless)
  • Mixing refactor + feature + typo
  • Committing secrets, logs, or build artifacts
  • Huge 2,000-line commits nobody reviews

Conventional Commits

A lightweight convention that enables automation.

type(scope): subject

feat(api): add pagination to list endpoint
fix(auth): refresh token on 401
refactor(cache): extract eviction policy
docs(readme): update setup steps
test(oee): cover daily-productivity fallback
chore(deps): bump trivy to v0.60
  • feat / fix / refactor / docs / test / chore — consistent vocabulary
  • Enables semantic-release, changelogs, and automatic versioning
  • Works great with squash-merge: the MR title becomes the commit

Guardrails for Commits

  • Add pre-commit hooks (lint, format, secret scan) so bad commits never happen
  • Use commitlint in CI to enforce the convention
  • Sign commits (git commit -S) where the team requires it
  • Rewrite history locally with rebase -i — but never force-push shared branches

Merge Request Best Practices

The MR is the unit of collaboration — and the last line of defense.

Small, Reviewable MRs

✅ Rule of thumb Keep MRs under ~300–400 lines and short-lived (merge within a day or two). Big MRs get shallow reviews.
  • One MR = one feature/fix. Split large work into stacked MRs
  • Include tests in the same MR as the change they cover
  • Keep the branch up to date with the target (rebase or merge main)
  • If it’s hard to describe in 3 sentences, it’s too big

A Great MR Description

## What & why
Adds a fallback to daily-productivity when `sabor` is not
populated by cam2/cam4, so OEE performance is no longer 0.

## Changes
- compute performance from global `padrao_linha_hora` rate
- add regression test with cam2-style rows

## How to test
- run `npm test`
- hit `/daily-productivity?date=2026-07-31`

## Screenshots / logs
- before: performance = 0 (empty group)
- after: 102.5% (cam2) · 97.1% (cam4)

Closes #123

Review Checklist

For the author

  • CI is green before asking for review
  • Self-review: re-read your own diff first
  • Link the issue; explain the “why”
  • Address feedback; don’t take it personally

For the reviewer

  • Review the behavior and tests, not just style
  • Ask questions instead of demanding rewrites
  • Be specific: “this could return null → add a test”
  • Approve fast when it’s good — don’t gate on perfection
Automate the checklist MR templates + required pipeline jobs = reviewers focus on logic, not housekeeping.

Merge Strategies

  • Squash merge: one clean commit per MR — great with Conventional Commits
  • Merge commit: preserves full history — useful for long-lived feature branches
  • Rebase merge: linear history — clean but requires discipline
  • Protect the default branch: no direct pushes, MRs only, CI required

Measuring Impact

You can’t improve what you don’t measure.

DORA Metrics

⚡ Deployment Frequency

How often we ship. More = smaller batches = less risk.

⏳ Lead Time for Changes

Commit → production. CI/CD shortens this dramatically.

🔄 Change Failure Rate

% of deploys causing failure. Tests + reviews + scans lower it.

🚑 MTTR

Time to restore service. Rollbacks & observability shrink it.

Targets (DORA high performers) Deploy on-demand · lead time < 1 day · failure rate < 15% · restore < 1 hour

Pipeline Health

  • Green rate: % of pipelines passing — if it’s low, the team ignores red
  • Duration: total pipeline time — keep the loop < 15 min for fast repos
  • Flaky test count: hunt flakes down; they destroy trust
  • Time to merge: from MR open to merge — short = healthy flow
  • Scanner findings trend: should go down, not up

Key Takeaways

🤖 Automate everything repetitive

Lint, test, build, scan, deploy — if it’s manual, it will be skipped under pressure.

✅ Tests are the control

Fast, reliable, meaningful. Block merge on failure and coverage drops.

🔒 Scan early, scan often

Secrets, SAST, SCA, images — shift left, block criticals, track the rest.

📝 Commit & MR hygiene

Atomic commits, Conventional Commits, small reviewable MRs with real descriptions.

The goal Ship faster with confidence. The pipeline is the guardrail that lets us accelerate without fear.
